# Private builders — one sealed builder per account, on the box you have

**Status:** PLAN, step 1 of the path to hosted multi-tenant building. Written
2026-10-20 after a code read-through of what runs today; awaiting the owner's
approval before anything on the box changes. Nothing here is live.
**Supersedes:** `migrate-box-runner-to-fcrunner.sh` (one dedicated user for one
runner — this is that idea, once per account).
**Related:** `multitenancy-execution-plan.md` (the boundary rule this keeps),
`box-owned-pty-executor.md` (the runner this templates), `models-and-money.md`
(who pays for models), `builders-and-booking.md` (builders on other people's
sites).

## One line

Every account that builds on the cloud gets its own Linux user on the box, with
its own home, its own token and its own agent sign-ins — and nobody's request
ever runs on another person's engine.

## Why now

A read-through on 2026-10-19 (four independent passes over the code) found:

1. **One builder, one identity.** `loki-box-runner.service` runs as `ubuntu`
   with the owner's Claude Code sign-in (`~/.claude`), the production
   `DATABASE_URL` and the org `GITHUB_TOKEN` in its environment, and every
   agent PTY inherits all of it (`local-pty.ts` spreads `process.env`). The
   runner's token is the owner's, so it only ever claims the owner's commands.
2. **A Builder on someone's project spends that someone's subscription.** A
   project member with the editor role asks for a change; the build runs as the
   project's owner, on the owner's Claude login, with no cap but 40 a day
   (`feedback/implement.ts`, `owner-build.ts`). Yesterday's client allowance
   (`config/client-allowance.ts`) rationed the same leak instead of closing it.
3. **A new account cannot build at all.** Every dispatch path defaults to the
   cloud channel and fails with `cloud-builder-private`; the kickoff screen then
   tells them to install Fleet Runner and try again, which fails the same way
   (`inject-core.ts` pins the channel before `decideQueuedExecution` can route
   to a connected local runner). "Hosted runner" is offered to everyone and
   queues work nothing claims (`hosted-runner.ts` serves the owner only).
4. **Chat and build are separate engines.** Only the agent CLIs change code
   (Claude Code by default; Codex, Gemini CLI, Grok, Cursor when installed).
   Loki's chat runs on free-tier Groq, Gemini and OpenRouter keys from the
   server env; a person's own stored key (`user_model_keys`) is chat-only and
   never serves anyone else. None of this needs to change.

The product cannot take a second customer who builds until (1) and (2) are
closed, and cannot keep a self-serve customer until (3) is.

## The rule

**Whoever asks for a change pays for it, with their own engine, in their own
builder.** An engine is one of:

- a Loki plan — Loki's own key, metered per build, paid through OrangeCat
  (built, switched off behind `LOKI_PAYMENTS_OPEN`; needs a changes-per-month
  cap before it is switched on);
- the person's own API key, pasted once in Settings;
- the person's own subscription, signed in with the CLI's own `/login` inside
  their private builder — exactly how the owner builds today.

A request from someone with no engine is a **suggestion** to the project's
owner, with one line saying how to get an engine. It never builds on the
owner's engine. (Welcome changes — a few free builds for a newcomer on Loki's
key with a monthly cap in CHF — are step C, not this step.)

## What step 1 changes

### On the box

- **A unit template** `loki-box-runner@<tenant>.service`, generated by
  `scripts/hetzner/new-tenant.sh <userId>`:
  - `User=lk-<short>` (a fresh system user), `HOME=/home/lk-<short>`,
    `LOKI_BOX_DEV_ROOT=/home/lk-<short>/dev`, its own
    `EnvironmentFile=/etc/loki/runners/<short>.env`;
  - `LOKI_RUNNER_PRESENCE_CHANNEL=cloud`, `LOKI_BOX_PREPARE=true`,
    `LOKI_RUNNER_UNATTENDED=true`, as today;
  - `ProtectSystem=strict`, `ProtectHome=tmpfs` + `BindPaths=` its own home,
    `InaccessiblePaths=` `/opt/loki`, `/home/ubuntu` and every `/opt/<app>`,
    `PrivateTmp`, `NoNewPrivileges`, `MemoryMax=3G`, `CPUQuota=200%`,
    `TasksMax=512`, `OOMPolicy=continue`.
- **A token per tenant.** `mint-box-runner-token.ts --user <id>` replaces
  `getSelfImprovementTarget()`. `/api/control/commands` already scopes claims by
  the token's user, so each unit drains only its own account's queue with no
  server change.
- **No database password in any runner.** The tenant `.env` carries the token,
  `LOKI_WEB_URL` and nothing else. `box-workspace.ts` stops reading the DB
  (`getSelfImprovementTarget`, `getUserProjects`) and asks the control plane for
  the project's `gitUrl` with the runner's token; it clones with the account's
  own GitHub token, served per run, never `process.env.GITHUB_TOKEN`.
- **Agents get an allowlisted environment.** `local-pty.ts` passes `PATH`,
  `HOME`, `TERM`, `LANG`, `USER` and the spec's own `env` — not `process.env`.
  This applies to the owner's runner too and is the single largest risk
  reduction in the plan: a visitor-fed task that tricks an agent today runs
  with production credentials in its environment.
- **The owner's runner moves onto the same template** (`lk-<owner>`), which
  retires `migrate-box-runner-to-fcrunner.sh` and `harden-box-runner.sh`. The
  owner signs in to Claude Code once in the new home. `install-box-runner.sh`
  and `deploy-hetzner.sh` restart every `loki-box-runner@*` unit instead of
  the one.

### In the app

- **Entitlement split.** `users.private_builder` (boolean, default false) is
  read by `getExecutionAccess` / `decideQueuedExecution` for the cloud channel.
  `isFleetInfrastructureAllowed` (org GitHub token, previews on the studio box,
  folder deletes, session reads, CD registration) stays founder-only. Today one
  predicate grants both; `LOKI_CLOUD_BUILDER_USER_IDS` is retired.
- **Routing honesty.** A project with no stored `builder_pref` on an account
  without cloud routes to its connected Fleet Runner instead of asking for the
  cloud and failing; kickoff writes `dirPath` under the tenant's own dev root,
  never the global `LOKI_BOX_DEV_ROOT`; "Hosted runner" is offered only to
  accounts the hosted runner serves.
- **Sessions on the cloud for a tenant** show their own unit's PTYs. Starting
  `claude` and typing `/login` signs in to their Claude account in their home.
  The same for `codex login`, `grok login --device-code`, `agent login`.
- **Settings → Your engine.** The existing key store (`user_model_keys`, sealed
  with `BYOK_SEAL_SECRET`) gains a "for building" use: a vendor key marked for
  builds is written into the tenant's unit environment on the next restart
  (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `XAI_API_KEY`, `CURSOR_API_KEY`).
  Today's keys stay chat-only unless the person chooses this.
- **Seats stop spending the owner's engine.** `askInLoki`, the member pass and
  `implementFeedback` run a member's request in the **member's** tenant when
  they have a private builder, and file it as a suggestion to the owner when
  they do not. `config/client-allowance.ts`, `on_allowance` and the per-site
  allowance UI are retired; "Make it live" and the member pass stay. The
  reply names the way forward: "To make changes yourself, add a way to build."
- **The 40-builds-a-day cap** moves from "per project, paid by the owner" to
  "per tenant, on that tenant's engine" — a guard against a runaway loop, not
  a pricing device.

### Deliberately not in step 1

- Containers or microVMs per build (steps 3–4; `SandboxExecutor` is the seed).
- The Loki plan switch-on, welcome changes, metering per run (step C).
- Builders from Bitbaum (step D) — they become ordinary tenants with a seat.
- Several boxes (roadmap "One box becomes a pool").

## Order of work — each line is one PR, verified before the next

1. **Stop the leak** (app only, no box change). A Builder's or client's request
   with no engine becomes a suggestion; the allowance is retired; the kickoff
   and "Hosted runner" false promises are fixed. Verified by
   `scripts/test/execution-access.ts` extended with the real dispatch path, and
   a walk as a fresh account on the live site.
2. **Environment allowlist for agent PTYs** (runner only). Verified by a
   dispatched agent printing `env` and the test asserting the allowlist.
3. **Runner without the database.** `box-workspace.ts` reads projects through
   the API; the runner `.env` loses `DATABASE_URL`. Verified by a clone-on-
   demand dispatch on the box with the variable removed.
4. **Unit template + token per tenant + `new-tenant.sh`.** Applied first to a
   second account of the owner's (a test tenant), then to the owner's own
   runner. Verified by: the test tenant signs in to Claude Code in its home,
   dispatches, builds; `sudo -u lk-test cat /opt/loki/app/.env` is refused;
   the owner's runner still builds; a deploy restarts both.
5. **Entitlement split and routing.** `users.private_builder`; the allowlist
   env retired; routing fixes. Verified by `execution-access.ts`.
6. **Settings → Your engine (for building)** and the tenant's Sessions page.
   Verified by a key marked for builds reaching the unit env and a build
   running on it.
7. **Manu.** `new-tenant.sh` for his account, his seat on Petvity set to
   "can change it", his own sign-in. The first real tenant is the acceptance
   test of the whole step.

Each PR is reversible on its own: a template unit can be stopped and the old
unit started; the allowlist env var is read until PR 5 removes it.

## Sealed builds (Track 4.2 of the master plan) — built, switched on by a reading

Each build in its own container inside the tenant's unit, so a tricked
agent cannot reach even its own tenant's other work:

- `SandboxExecutor` has a **podman** mode (`sandbox.ts buildPodmanRunArgs`):
  rootless, as the tenant (`--userns=keep-id`), the tenant's home bound at
  the same path (sign-ins, trust and transcripts stay where the runner
  looks), the project's real path as workdir, network on, capabilities
  dropped, `--cgroups=disabled` so the deploy's drain still counts the
  processes, and gVisor's `runsc` as the OCI runtime when the box has it
  (no KVM needed; the CX43 has none).
- `scripts/hetzner/agent-image/Containerfile` is the image (a shell, git,
  Cursor, Grok, Antigravity, opencode,
  gh, node, Claude Code, Codex); `install-sealed-builds.sh`, run by every
  deploy, installs rootless podman, tries runsc, builds the image into a
  shared read-only store, and writes a READING to `/etc/loki/sealed-builds`
  (`ready`, and `runsc` when it is there).
- **Nothing switches on by itself.** `new-tenant.sh` adds the unit drop-in
  (`LOKI_EXECUTOR=sandbox`, `LOKI_SANDBOX_RUNTIME=podman`, runsc when read)
  only when the reading says `ready` AND the operator has put
  `/etc/loki/sealed-builds.on` in place after watching one tenant build
  inside a container. Until then every tenant builds unsealed, exactly as
  before, and the roadmap milestone stays unticked. Why: the pieces are
  verified by unit tests and the deploy's readings, not yet by a build on
  the box, and `NoNewPrivileges` in the unit means rootless podman runs in
  its single-uid mapping — enough for the agent CLIs, to be confirmed live.

## Booked builders (Track 3 of the master plan) — a seat, a fee, OrangeCat's word

A partner approved on the studio's partner track is booked by assignment,
and the pieces are the ones above, used for one more person:

- **The seat** (`lib/studio/seat.ts`): assigning a partner to a website brief
  resolves the partner's Loki account (the `users.orangecat_actor_id` their
  connected OrangeCat identity names) and makes them an **editor on the
  brief's linked project** — `project_memberships`, never an org — and
  switches their private builder on, so their builds run under
  `lk-<short>` on their own engine. The seat follows the two facts it rests
  on (assignment, project link) and goes when either does. A partner with no
  Loki account yet has no seat until they sign in with OrangeCat.
- **The fee** (`lib/studio/fee.ts`, `fee-listing.ts`,
  `integrations/orangecat-fee-service.ts`): with a delivery the partner may
  state a fee once; after the delivery is saved Loki lists it as a service in
  the **partner's own name** on OrangeCat with the partner's own token
  (`service.write`, asked for at sign-in), live at once and off their profile.
  The brief shows the link; the client pays at OrangeCat, to the partner's
  wallet. Loki holds no money and no key of theirs.
- **Paid** is a fact OrangeCat states: its settled-payment signal
  (`/api/orangecat/events`, `markStudioFeePaid`) is the one path that marks
  a brief paid, idempotent on the payment, and both sides are told.

## What could go wrong

- **Memory.** A CX43 (8 vCPU, 16 GB) carries roughly 6–10 concurrent Claude
  Code sessions. `MemoryMax` per unit keeps one tenant from taking the box
  down; the first symptom of growth is queued builds, read on System
  ("Capacity you can read" on the roadmap). The next size is CX53 (32 GB,
  about CHF 35/month) or overflow to rented VMs at roughly 1–2 rappen per
  build. No money is spent until that reading says so.
- **Claude Code sign-in in a headless home.** The owner's current setup is a
  sign-in in `~/.claude` under `ubuntu`. A tenant signs in from the web
  terminal (`/login` → browser → code pasted back), the flow the owner used.
  If the CLI's device flow breaks for a version, `claude setup-token` on a
  laptop and the token in the unit env is the fallback.
- **Vendor terms.** A person's consumer subscription inside their *own*
  private builder matches how Claude Code, Codex and Grok are meant to be
  used. One shared sign-in serving many people would not; this design makes
  that impossible by construction.
- **Previews.** Studio previews stay on the owner's tenant (they are the
  owner's client work). A tenant's own site is an ordinary project in the
  tenant's dev root; the `<name>.orangecat.ch` host attach stays founder-only
  until "One box becomes a pool".
- **The two "operator" definitions** (`users.isDefault` vs the owner of the
  `loki` entity) are unified on `isDefault` in PR 5.

## Cost

CHF 0 in hosting. Everything runs on the existing CX43. The owner's Claude
Max, ChatGPT Plus and Grok subscriptions build only the owner's own work.
